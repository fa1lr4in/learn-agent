**从零开发 Agent ①：跑通模型 API、多轮对话和第一次工具调用**

我准备从零开发一个自己的 Agent，并把开发过程公开在 GitHub 上。

我的起点是：主要会 Python，借助 AI 能大概看懂代码。最初对 Agent 的理解也很直接——调用大模型 API，让模型帮我操作电脑。

真正开始动手后，我发现，这句话里藏着不少问题：

程序到底给模型发送了什么？模型为什么能记住上一轮对话？它返回一句“我来读取文件”，本地文件就真的被读取了吗？

这一阶段，我从一个终端程序开始，逐步跑通了模型调用、多轮对话和一次真实的文件读取。这篇文章把代码、运行过程和实验结果放在一起，记录我对这些问题的理解。

接下来，先看一次模型调用究竟发送了什么。

在项目目录中运行：

```powershell
python chat.py --preview "请用一句话解释 Agent。"
```

`--preview` 只展示请求，不发送网络请求，也不需要读取密钥。

终端会打印出这样的请求体：

```json
{
  "model": "deepseek-flash",
  "messages": [
    {
      "role": "system",
      "content": "你是一位编程老师，用简洁的中文回答问题。"
    },
    {
      "role": "user",
      "content": "请用一句话解释 Agent。"
    }
  ],
  "stream": false,
  "thinking": {
    "type": "disabled"
  },
  "max_tokens": 512
}
```

这里最值得先认识的是 `messages`。

`system` 消息来自我们的程序，用于提供基本指令；`user` 消息来自用户输入。模型生成的回答，则属于 `assistant` 消息。

其他几个字段也能直接对应到程序行为：`model` 指定模型，`stream: false` 表示等待完整响应，`thinking` 在本次实验中关闭思考模式，`max_tokens` 限制本次生成的最大 token 数量。

> 【配图 2：第一次看见完整请求】
>
> 截图内容：预览命令、完整 JSON 请求体，以及末尾“预览结束，没有发送网络请求”的提示。
>
> 图注：模型调用的输入由程序组织，系统指令和用户问题都能在请求体中找到。

去掉 `--preview`，才会真正调用模型：

```powershell
python chat.py "请用一句话解释 Agent。"
```

在代码中，`call_model()` 负责把请求体编码为 JSON，通过 HTTP POST 发送给 DeepSeek，再把返回的 JSON 解析成 Python 字典。

程序会同时展示完整响应和单独提取出来的助手回答。我希望先看清接口返回了哪些信息，再逐步考虑界面怎么呈现。

**第一次真实调用后，我做了一个输出长度对照实验。**

`chat.py` 中有这样一个配置：

```python
"max_tokens": 512,
```

我把它改成 `10`，重新运行；随后又改回 `512`。

补做这个实验时，应使用同一个问题，并保持其他参数一致，这样更容易观察输出长度限制带来的变化。

这次实际观察到：

| 配置 | 运行现象 |
|---|---|
| `max_tokens = 512` | 回答正常结束 |
| `max_tokens = 10` | 输出受到长度限制，停止原因变为 `length` |
| 改回 `512` | 回答恢复正常结束 |

Token 是模型处理文本的计量单位，不能简单理解为汉字数量。因此，`max_tokens = 10` 限制的是最多生成 10 个 token。

> 【配图 3、4：512 与 10 的实际返回对照】
>
> 建议把两张截图并排放置，左边为 `512`，右边为 `10`。
>
> 每张截图需要保留：
>
> - 请求中的 `max_tokens`。
> - `[模型服务返回的 JSON]` 中的 `choices` 和 `usage`。
> - `[助手回答]`。
> - 停止原因和 token 用量。
>
> 如果一屏放不下，可以分别截取请求参数和返回结果，再拼成上下结构。
>
> 图注：同一问题在两种输出上限下的实际表现。`max_tokens = 10` 时，本次生成以 `length` 结束。

这两张图里，DeepSeek 返回的详情值得仔细看：

| 字段 | 我用它观察什么 |
|---|---|
| `choices[0].message.content` | 模型实际生成的文本 |
| `choices[0].finish_reason` | 本次生成为什么结束 |
| `usage.prompt_tokens` | 本次请求的输入 token 数量 |
| `usage.completion_tokens` | 本次生成的输出 token 数量 |
| `usage.total_tokens` | 本次请求的总 token 数量 |

接口对这些字段的含义有明确说明，可以对照 [DeepSeek 官方接口文档](https://api-docs.deepseek.com/api/create-chat-completion/) 阅读。

这个实验让我开始关注回答之外的状态。程序收到一段文字后，还需要检查它是否正常结束。尤其是后续模型要生成工具参数时，截断的输出可能无法继续使用。

完成实验后，我把 `max_tokens` 恢复成了 `512`。

**接下来，我让程序支持连续对话。**

运行：

```powershell
python chat.py --chat "我的项目叫小灯。"
```

收到第一轮回答后，继续输入：

```text
我的项目叫什么？
```

模型能够正确回答“小灯”。

这个能力对应的代码很短。模型回答后，把回答加入历史：

```python
messages.append({"role": "assistant", "content": content})
```

用户继续提问时，再把新问题加入历史：

```python
messages.append({"role": "user", "content": prompt})
```

下一次请求会重新发送这些消息。因此，第二次请求里的消息顺序是：

```text
system     基本指令
user       我的项目叫小灯。
assistant  模型的第一轮回答
user       我的项目叫什么？
```

> 【配图 5：模型为什么知道项目名】
>
> 截图内容：第二次请求中的完整 `messages`，以及模型正确回答项目名的结果。第一条用户消息和最后一条追问都要能看清。
>
> 图注：项目名仍在第二次请求的消息历史中，模型可以根据上下文回答。

为了进一步验证，我加入了 `/clear` 命令。

在同一个对话中输入：

```text
/clear
我的项目叫什么？
```

清空历史的关键代码是：

```python
del messages[1:]
```

列表中的第一条消息是系统指令。这一行会保留它，删除后面的用户消息和助手回答。

实际运行后，下一次请求里只剩系统指令和新问题，模型也不知道项目名了。

> 【配图 6：清空历史后的对照】
>
> 截图内容：输入 `/clear` 的过程、清空提示、下一次请求中仅有两条消息的 `messages`，以及模型不知道项目名的回答。
>
> 图注：清空历史后，后续请求不再携带项目名，模型失去了回答这个问题所需的信息。

对当前这个程序来说，“记忆”的来源已经可以在代码中找到：程序保存历史，并在后续请求中重新发送。

这些历史目前只保存在进程内存里，退出程序后就不保留。

**最后一步，是让模型用到一份真实的本地文件。**

我准备了 `workspace/project.txt`：

```text
这是用于学习工具调用的公开练习文件。
项目名称：小灯
开发语言：Python
项目目标：逐步构建一个编程 Agent。
本次实验编号：7391
```

任务是读取文件，准确回答项目名称和实验编号。

选择这两个字段，方便直接把回答与文件原文对照，检查整个读取流程是否接通。

> 【配图 7：工具要读取的原始文件】
>
> 截图内容：编辑器中打开的 `workspace/project.txt`，保留文件路径和完整内容。
>
> 图注：模型需要通过工具获得的原始资料，其中包含项目名称和实验编号。

程序首先要向模型说明工具如何使用。下面是 `TOOLS` 中的函数定义：

```json
{
  "name": "read_file",
  "description": "读取练习目录中的 project.txt，获取真实的项目资料。",
  "parameters": {
    "type": "object",
    "properties": {
      "path": {
        "type": "string",
        "enum": ["project.txt"]
      }
    },
    "required": ["path"],
    "additionalProperties": false
  }
}
```

这段定义告诉模型：工具叫什么、用途是什么、需要提供什么参数。

此时发送的是工具说明，文件正文尚未发送。

运行：

```powershell
python tool_call.py
```

模型第一次回复时，会提出工具调用请求。需要观察 `tool_calls` 中的几个字段：

- `id`：本次工具请求的标识。
- `function.name`：模型请求调用的工具名称。
- `function.arguments`：模型生成的参数，是包含 JSON 内容的字符串。

> 【配图 8：模型提出读文件请求】
>
> 截图内容：`[第一次模型回复：检查 tool_calls]` 中的完整工具请求，以及下面等待输入 `y` 的提示。
>
> 图注：模型已提出 `read_file` 请求，程序正在等待确认，尚未读取文件。

程序收到请求后，会检查工具名称、参数结构和文件路径。输入 `y` 后，才执行本地的读取函数：

```python
def read_file(path: str) -> str:
    if path != "project.txt":
        raise ValueError("本课只允许读取练习文件 project.txt。")
    return (
        Path(__file__).parent / "workspace" / "project.txt"
    ).read_text(encoding="utf-8")
```

这里发生了真正的文件访问：Python 打开文件并读出文本。

接着，程序把工具结果追加到消息历史：

```python
{
    "role": "tool",
    "tool_call_id": tool_call["id"],
    "content": result,
}
```

`content` 是刚刚读取到的真实内容，`tool_call_id` 对应模型提出工具请求时的 `id`。

第二次模型请求中的历史因此包含四部分：

```text
system     基本指令
user       读取文件并回答问题的任务
assistant  模型提出的工具调用请求
tool       Python 实际读取的文件内容
```

模型收到第二次请求后，依据工具结果生成回答。

这次真实运行中，回答的项目名和实验编号都与文件一致。

到这里，一次工具调用的完整过程就串起来了：

```text
用户提出问题
    ↓
程序发送问题和工具说明
    ↓
模型提出工具调用请求
    ↓
程序检查参数，用户确认
    ↓
Python 读取本地文件
    ↓
程序把读取结果交回模型
    ↓
模型根据真实结果回答
```

**模型提出请求，程序执行操作。** 这句话，是我在这一阶段最重要的收获。

工具描述帮助模型理解工具如何使用；允许读取哪些文件、什么时候执行、执行哪段代码，则由本地程序控制。

工具部分目前是固定流程：第一次请求让模型决定是否调用工具，执行后发送第二次请求，让模型根据结果回答。
