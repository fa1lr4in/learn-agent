# 从零开发 Agent（四）：让它修改项目，并通过测试验收

上一篇，我们为 Agent 加入了文件写入、运行日志和工具授权。它已经能读取资料、整理报告，并把结果真正保存到电脑上。

但编程助手还需要走完更长的一段路：找到项目里的代码，理解修改要求，保存变更，运行测试，再根据结果决定下一步。

这一阶段，我用一个很小的 Python 项目完成了这次实验。任务只是给统计函数增加最小值和最大值，却把源码读取、代码修改、失败反馈和结果验收串了起来。

实际运行中，第一次验收的 4 个用例全部失败。模型修改业务代码后，4 个用例全部通过，项目入口也输出了正确结果。整个任务用了 5 次模型请求。

本文记录这段开发过程，也提供对应代码和复现命令。项目地址：[fa1lr4in/learn-agent](https://github.com/fa1lr4in/learn-agent)。

## 2. 先把代码执行结果交回模型

在修改多文件项目之前，我先给 Agent 加入了 `run_python` 工具。

第一个实验很简单：生成 `workspace/main.py`，计算 1 到 100 的整数和，然后真正运行它。模型提出调用请求，本地 Python 程序启动子进程，取得输出 `5050`，再把结果交给模型。

`tool_call.py` 中的关键实现如下，省略了函数文档字符串：

```python
def run_python(path: str) -> subprocess.CompletedProcess[str]:
    target = resolve_python_path(path)
    if not target.is_file():
        raise FileNotFoundError(f"{path} 不存在或不是普通文件。")
    child_env = os.environ.copy()
    child_env.pop("DEEPSEEK_API_KEY", None)
    return subprocess.run(
        [sys.executable, "-E", "-s", "-B", "-X", "utf8", str(target)],
        cwd=target.parent,
        env=child_env,
        stdin=subprocess.DEVNULL,
        capture_output=True,
        text=True,
        encoding="utf-8",
        errors="replace",
        timeout=RUN_TIMEOUT,
    )
```

这里有几个直接影响行为的设置。

`resolve_python_path()` 检查目标是否位于工作目录内、后缀是否为 `.py`。`sys.executable` 使用启动 Agent 的同一个 Python 解释器。`cwd=target.parent` 让脚本在自己的目录中运行，能够按相对路径读取项目资料。

启动参数保留了脚本目录的模块搜索能力，所以后面入口文件里的 `from src.stats import summarize` 可以正常导入。执行过程关闭标准输入，最长运行 10 秒，并捕获输出。

工具将执行结果整理为下面的结构：

```python
completed = run_python(arguments["path"])
result = {
    "ok": completed.returncode == 0,
    "tool": name,
    "path": arguments["path"],
    "exit_code": completed.returncode,
    "stdout": completed.stdout,
    "stderr": completed.stderr,
}
```

这段代码位于工具分发逻辑中。`result` 随后被编码成 JSON，作为一条 `role: tool` 消息进入下一次模型请求。模型拿到的是实际退出码和输出，再据此判断是否需要继续处理。

## 3. 正常退出不等于满足需求

最初，我用一个拼写错误验证修复能力：把 `numbers` 写成 `nubmers`。第一次运行得到真实的 `NameError`，模型根据 `stderr` 修正源码，再次运行成功。

更有意思的是另一段代码：

```python
def sum_to(n):
    return sum(range(1, n))
```

它可以正常退出，但计算 1 到 100 的和时会得到 `4950`，因为 `range` 不包含上界。

这说明 `exit_code: 0` 只表示程序正常退出，无法证明计算结果符合要求。为此，项目加入了固定验收脚本，检查 `sum_to(0)`、`sum_to(1)`、`sum_to(10)` 和 `sum_to(100)`，让断言明确指出错误。

从这里开始，开发过程多了一条约束：**完成修改以后，需要用独立的验收条件检查结果。** 接下来的多文件实验继续沿用这个做法。

## 4. 用一个小项目定义修改目标

本次练习项目的结构如下：

```text
workspace/
└── demo_project/
    ├── README.md
    ├── main.py          # 入口，准备输入并展示结果
    ├── test_stats.py    # 固定验收脚本
    └── src/
        └── stats.py     # 统计业务逻辑
```

入口 `demo_project/main.py` 负责导入和调用业务函数：

```python
from src.stats import summarize


def main():
    values = [12, 18, 30]
    print(summarize(values))


if __name__ == "__main__":
    main()
```

初始的 `src/stats.py` 只返回数量、总和和平均值：

```python
def summarize(values):
    count = len(values)
    total = sum(values)
    return {
        "count": count,
        "total": total,
        "average": total / count if count else 0.0,
    }
```

在此前的只读实验中，Agent 已经能浏览目录，再沿着 `import` 找到这个函数，推算出输入 `[12, 18, 30]` 时的三个统计值。那次没有运行程序，结论来自源码阅读。

这次需要在此基础上增加 `min` 和 `max` 两个字段；空列表时，两者均为 `None`；已有字段继续保留。

> 【截图 02：项目结构与初始代码】项目文件树、入口中的导入语句，以及尚未增加新字段的 `stats.py`。

验收脚本 `demo_project/test_stats.py` 随复现版本提供，覆盖四组输入：

| 输入 | 原有统计结果 | 新增字段的预期值 |
| --- | --- | --- |
| `[12, 18, 30]` | 数量 3，总和 60，平均值 20.0 | 最小值 12，最大值 30 |
| `[]` | 数量 0，总和 0，平均值 0.0 | 两个字段均为 `None` |
| `[7]` | 数量 1，总和 7，平均值 7.0 | 两个字段均为 7 |
| `[-5, -2, -9]` | 数量 3，总和 -16，平均值为 -16 / 3 | 最小值 -9，最大值 -2 |

例如，空列表用例这样检查返回值，以下是测试类中的方法节选：

```python
def test_empty_list(self):
    self.assertEqual(summarize([]), {
        "count": 0, "total": 0, "average": 0.0,
        "min": None, "max": None,
    })
```

这份固定脚本被列入 `write_file` 的只读范围。本次只允许修改业务模块，入口和验收条件保持原样。

## 5. 把需求交给 Agent

在实验副本的根目录，先保存任务提示。预览命令可以检查请求，不联网、不执行工具；正式运行才会请求模型：

```powershell
$taskPrompt = @'
请为 demo_project/src/stats.py 的 summarize(values) 增加 min 和 max 两个字段，空列表时这两个字段均为 None，保留原有 count、total、average 的行为。
先读取 demo_project/src/stats.py 和 demo_project/test_stats.py，再运行 demo_project/test_stats.py 观察现有结果。
只修改 demo_project/src/stats.py，不要改写或跳过测试，也不要修改入口文件。修改后再次运行 demo_project/test_stats.py，并运行 demo_project/main.py。
最后根据真实工具结果简要说明改动、测试和程序输出。

python -B -X utf8 tool_call.py --auto-read --preview $taskPrompt
```

确认请求内容后，在同一个 PowerShell 窗口运行：

```powershell
python -B -X utf8 tool_call.py --auto-read $taskPrompt
```

`--auto-read` 自动批准读取。写入和运行仍逐次询问，需要检查提示后输入 `y`。

本次真实运行记录了下面的过程：

| 模型请求 | 提出的操作 | 实际结果 |
| --- | --- | --- |
| 第 1 次 | 同轮读取业务源码和验收脚本 | 两次读取成功，自动批准 |
| 第 2 次 | 运行 `demo_project/test_stats.py` | 确认后执行，4 项测试失败 |
| 第 3 次 | 写入新的 `demo_project/src/stats.py` | 展示完整内容，确认后保存 |

合计 **5 次模型请求、6 次工具调用、4 次人工确认**。一次模型回复可以包含多个工具请求，当前程序会按顺序执行。再次调用模型时，工具分组和请求次数可能变化。

## 6. 从失败反馈到源码修改

第一次验收返回 `ok: false`、`exit_code: 1`。普通列表用例中的断言比较是：

```text
AssertionError: {'count': 3, 'total': 60, 'average': 20.0} != {'count': 3, 'total': 60, 'average': 20.0, 'min': 12, 'max': 30}
```

报告末尾记录：

```text
Ran 4 tests in 0.002s

FAILED (failures=4)
```

四项失败都指向同一个缺口：返回字典中缺少 `min` 和 `max`。Agent 循环把错误报告交回模型，使这次失败成为后续修改的依据。

> 【截图 04：第一次验收失败】工具路径、`ok: false`、`exit_code: 1`，以及一条代表性断言和 `FAILED (failures=4)`。

收到失败信息后，模型请求用 `write_file` 保存下面的完整源码：

```python
def summarize(values):
    count = len(values)
    total = sum(values)
    return {
        "count": count,
        "total": total,
        "average": total / count if count else 0.0,
        "min": min(values) if count else None,
        "max": max(values) if count else None,
    }
```

新增逻辑只有两个字段。空列表时 `count` 为 0，直接返回 `None`，避免对空列表调用 `min()`、`max()`。

终端先展示即将写入的完整内容，询问是否覆盖；输入 `y` 后才保存，随后工具返回 `ok: true`。当前工具仍采用整文件覆盖，即使只增加两行，模型也需要提交完整内容。

## 8. 用日志区分计划执行与实际发生的操作

一个完整任务里，模型可能提出操作，也可能在真正执行前被拒绝或因预算限制停止。日志需要记录这些差别。

本文版本逐条保存模型请求、回复、工具授权、工具结果和结束原因。在完成一次正式任务后，从项目根目录执行以下命令，会自动读取最近生成的日志：

```powershell
$runLog = Get-ChildItem -LiteralPath .\logs -Filter *.jsonl -File |
    Sort-Object LastWriteTime | Select-Object -Last 1
$events = Get-Content -LiteralPath $runLog.FullName -Encoding UTF8 |
    ForEach-Object { $_ | ConvertFrom-Json }

$events | Where-Object { $_.event -eq "tool_result" } |
    ForEach-Object {
        [pscustomobject]@{
            step      = $_.step
            tool      = $_.result.tool
            path      = $_.result.path
            ok        = $_.result.ok
            exit_code = $_.result.exit_code
        }
    } | Format-Table -AutoSize

$events | Where-Object { $_.event -eq "tool_approval" } |
    Select-Object step, tool, approved, source |
    Format-Table -AutoSize

$events | Select-Object -Last 1 | ConvertTo-Json
```

本次事件表能对应上 6 次工具调用，以及读取自动批准、写入和运行人工批准的记录。最后一条事件是 `run_end`，`reason` 为 `stop`。日志不包含密钥，并被 Git 忽略；其中仍可能保存项目内容，适合留在本机检查。

> 【截图 10：日志与授权总览】工具结果表、授权来源，以及最后的 `run_end.reason: stop`。

这一阶段还处理过两种容易混淆的停止情况。

第一种是模型请求次数用完。早期上限为 5 次，有一次任务已完成部分修改和测试，却没有余量继续验证。当前上限调整为 8，包含最后一次回答。

第二种是输出被截断。曾经测试和入口已经运行成功，但最终回答在 `max_tokens: 512` 时被截断。工具循环后来将输出上限调整为 2048；如果仍收到 `length`，会明确报告回复不完整，并保留此前结果。

对于正常结束或因请求次数上限停止的任务，`--resume` 可以重新加载消息历史。尚未执行的工具请求会补为 `NotExecuted`。恢复历史不会自动重放操作；模型如需继续，必须重新提出请求，再经过本次权限检查和确认。

我已经验证过这个区别：旧运行请求没有被自动执行，模型新提出的 `main.py` 请求在确认后才输出 `5050`。会话里记得某个操作，与本次真正执行了它，是两件不同的事。

## 10. 从这个实验理解编程 Agent

最初，我对 Agent 的理解是“调用模型 API，让模型帮忙操作电脑”。这次实验让我看清了中间的具体分工。

用户提出需求，模型根据源码和工具反馈选择行动；本地程序负责检查路径、询问授权、修改文件和运行代码；测试给出可检查的结果，再成为下一轮模型请求的输入。

这次任务完成的依据，是磁盘上确实出现了预期修改，固定测试通过，入口输出正确，日志也能对上实际执行过程。模型的最终回答把这些结果整理出来。

这个 Agent 目前还很小：编辑采用整文件覆盖，工作目录固定，四项测试只覆盖本次需求。文件工具的路径检查也不等于操作系统沙箱；虽然子进程移除了直接继承的模型密钥环境变量，脚本仍拥有当前账户允许的其他文件和网络访问能力。

下一步，我准备补上局部编辑、搜索和差异检查。随着项目变大，这些能力会决定它能否更准确地找到代码、控制修改范围，并把每一次变更交给使用者核对。
