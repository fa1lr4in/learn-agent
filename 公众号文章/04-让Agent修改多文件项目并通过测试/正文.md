上一篇，我的 Agent 已经能读取资料、生成报告，把工具授权和执行结果写进日志。

这次，我想让它完成一个更接近编程助手的任务：读懂一个小项目，为现有函数增加功能，运行测试，再根据真实结果判断有没有完成。

最后的结果是：第一次验收的 4 个用例全部失败；模型修改业务代码后，4 个用例全部通过；项目入口打印出了新增的最小值和最大值，任务正常结束。

这篇文章记录从“写出代码”到“修改项目并验证结果”的过程。项目仍然是我在 AI 辅助下逐步开发的 Python Agent，代码公开在 [fa1lr4in/learn-agent](https://github.com/fa1lr4in/learn-agent)。

## 先让代码真正运行起来

在进入多文件项目之前，我先补上了执行 Python 的能力。

最初的实验是让 Agent 生成 `workspace/main.py`，计算 1 到 100 的整数和。文件写入后，还需要调用 `run_python`，由本地程序启动子进程，取得真实输出 `5050`。

这个工具的核心代码如下，来自当前版本的 `tool_call.py`：

```python
def run_python(path: str) -> subprocess.CompletedProcess[str]:
    target = resolve_python_path(path)
    if not target.is_file():
        raise FileNotFoundError(f"{path} 不存在或不是普通文件。")
    child_env = os.environ.copy()
    child_env.pop("DEEPSEEK_API_KEY", None)
    return subprocess.run(
        [sys.executable, "-E", "-s", "-B", "-X", "utf8", str(target)],
        cwd=target.parent,
        env=child_env,
        stdin=subprocess.DEVNULL,
        capture_output=True,
        text=True,
        encoding="utf-8",
        errors="replace",
        timeout=RUN_TIMEOUT,
    )
```

`resolve_python_path()` 检查路径边界和 `.py` 后缀。实际启动哪个解释器、在哪个目录运行、怎样捕获输出，都是宿主程序的职责。

这里的 `cwd=target.parent` 在后面的多文件项目里尤其有用：脚本在自己所在的目录运行，能够读取项目内的相对路径资料。启动参数保留脚本目录的模块搜索能力，因此入口里的 `from src.stats import summarize` 也能正常导入。

工具把运行情况整理为三个关键字段，再通过原来的 Agent 循环交回模型：

```python
completed = run_python(arguments["path"])
result = {
    "ok": completed.returncode == 0,
    "tool": name,
    "path": arguments["path"],
    "exit_code": completed.returncode,
    "stdout": completed.stdout,
    "stderr": completed.stderr,
}
```

先前读文件得到的是正文；现在执行代码得到的是退出码和输出。它们都作为 `role: tool` 的消息进入下一次请求，模型据此决定继续修改还是结束任务。

## 能正常退出还不足以验收代码

我先做过一次错误恢复实验：故意把变量名 `numbers` 写成 `nubmers`。第一次运行返回 `NameError`，模型根据 `stderr` 修正，再运行得到 `5050`。

随后又遇到另一类问题：

```python
def sum_to(n):
    return sum(range(1, n))
```

这段程序可以正常运行，却会把 1 到 100 的和算成 `4950`，因为 `range` 不包含上界。`exit_code` 为 `0`，只能说明程序正常退出。

为此，练习目录加入了固定验收脚本，检查 `sum_to(0)`、`sum_to(1)`、`sum_to(10)`、`sum_to(100)`。模型必须根据断言失败修正计算逻辑，再次运行测试。

这些实验让我开始把两件事分开看：**工具有没有成功执行，以及执行结果是否满足需求。** 下面的多文件任务继续沿用这套验收方式。

## 先写清楚验收条件

`demo_project/test_stats.py` 使用标准库 `unittest`，固定检查四类输入：

| 输入 | 原有统计结果 | 新增字段的预期值 |
| --- | --- | --- |
| `[12, 18, 30]` | 数量 3，总和 60，平均值 20.0 | 最小值 12，最大值 30 |
| `[]` | 数量 0，总和 0，平均值 0.0 | 两个字段均为 `None` |
| `[7]` | 数量 1，总和 7，平均值 7.0 | 两个字段均为 7 |
| `[-5, -2, -9]` | 数量 3，总和 -16，平均值为 -16 / 3 | 最小值 -9，最大值 -2 |

例如，普通列表和空列表的用例如下：

```python
import unittest

from src.stats import summarize


class SummarizeTests(unittest.TestCase):
    def test_regular_numbers(self):
        self.assertEqual(summarize([12, 18, 30]), {
            "count": 3, "total": 60, "average": 20.0,
            "min": 12, "max": 30,
        })

    def test_empty_list(self):
        self.assertEqual(summarize([]), {
            "count": 0, "total": 0, "average": 0.0,
            "min": None, "max": None,
        })
```

这是验收脚本的节选，完整文件还包含单个数字和负数两项测试，以及 `unittest.main()` 入口。

这份验收脚本随项目提供，并列入 `write_file` 的只读范围。当前任务要求只修改业务源码，保留入口和验收条件。

## 模型提出修改本地程序负责保存

拿到失败信息后，模型请求用 `write_file` 保存以下完整源码：

```python
def summarize(values):
    count = len(values)
    total = sum(values)
    return {
        "count": count,
        "total": total,
        "average": total / count if count else 0.0,
        "min": min(values) if count else None,
```

真正新增的业务逻辑只有最后两个字段。`count` 为 0 时直接返回 `None`，避免对空列表调用 `min()` 或 `max()`。

## 从日志核对整个过程

日志保存在本机，已被 Git 忽略。文章展示必要的结果节选，不上传完整运行历史。

在 PowerShell 中，可以把这份记录整理成事件表：

```powershell
$runLog = ".\logs\run-20261018-164020-514723.jsonl"
$events = Get-Content -LiteralPath $runLog -Encoding UTF8 |
    ForEach-Object { $_ | ConvertFrom-Json }

$events | Where-Object { $_.event -eq "tool_result" } |
    ForEach-Object {
        [pscustomobject]@{
            step      = $_.step
            tool      = $_.result.tool
            path      = $_.result.path
            ok        = $_.result.ok
            exit_code = $_.result.exit_code
        }
    } | Format-Table -AutoSize

$events | Where-Object { $_.event -eq "tool_approval" } |
    Select-Object step, tool, approved, source |
    Format-Table -AutoSize

$events | Select-Object -Last 1 | ConvertTo-Json
```

自己重新运行时，把 `$runLog` 换成本次终端显示的日志文件路径。表里应能对应上两次读取、一次失败验收、一次写入、两次成功运行，以及读取自动批准、写入和运行人工批准的记录。

## 中断以后如何继续也需要说清楚

从生成求和脚本到完成这次项目修改，中间还处理过几类问题。

最早的模型请求上限是 5 次。有一次任务已经做了部分修改和测试，却没有剩余请求完成后续验证，程序按上限停止。后来上限调整为 8，并明确把最终回答需要的请求也算进去。

输出预算则是另一回事。曾经出现测试和入口都运行成功，但最终回答在 `max_tokens: 512` 时被截断。工具循环后来将这个上限改为 2048；如果服务仍返回 `length`，程序会报告输出不完整，保留已完成的工具结果，而不会标记为正常完成。

| 限制 | 当前值 | 约束对象 |
| --- | --- | --- |
| 模型请求次数 | 每次任务最多 8 次 | 包含最后一次回答 |
| 模型输出长度 | 每次请求最多 2048 token | 单次回复，包括工具请求参数 |
| Python 执行超时 | 10 秒 | 直接启动的 Python 子进程 |

为了接上先前任务，程序增加了 `--resume`。它把旧日志里的消息重新组织到新请求中。正常结束的会话可以继续问；因请求上限停止的会话，会为尚未执行的工具请求补上 `NotExecuted` 状态。

关键是，恢复历史不会自动重放旧工具。需要继续运行时，模型必须重新提出请求，再经过本次权限检查和确认。我已经验证过旧请求没有自动执行，新提出的 `main.py` 运行请求在输入 `y` 后才得到 `5050`。

这些能力没有替代本次的测试验收，但使“任务为什么停下、哪些操作真的发生过、继续时该做什么”变得可以检查。

## 这次学习以后我怎样理解编程 Agent

最初，我把 Agent 理解为“调用模型 API，让模型帮我操作电脑”。这次实验把这句话里的几个环节拆开了。

用户给出需求；模型读取工具返回的信息，提出修改和运行请求；宿主程序检查路径、询问授权、操作文件并启动子进程；测试提供可检查的反馈；模型拿到结果后再决定下一步。

这次任务最终完成的依据，是磁盘上的业务代码确实增加了两个字段，四项测试通过，入口输出正确，执行记录也完整。最终回答把这些证据整理给我。

目前的能力仍有明确范围：编辑工具保存完整文件；工作目录固定；路径检查只约束这些文件工具；执行 Python 没有操作系统沙箱。子进程移除了直接继承的 `DEEPSEEK_API_KEY` 环境变量，但脚本仍拥有当前账户允许的其他文件和网络访问能力。固定验收脚本的只读限制也只是文件工具的规则。

四项测试能证明满足本次需求，不能证明任意输入都正确。下一阶段，我准备继续补上局部编辑、搜索和修改差异检查，让同一套过程能够用于更实际的项目。
