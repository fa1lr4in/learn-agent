# 从零开发 Agent（二）：让模型连续调用工具，并学会处理失败

上一篇，我用 Python 跑通了 DeepSeek API、多轮对话，以及第一次真实的文件读取。

当时的程序已经可以完成这样一件事：模型提出读取 `project.txt`，我在终端输入 `y`，Python 读取本地文件，再把内容发给模型。模型最后根据文件回答问题。

但只读一次文件还不够。假如项目资料里写着“任务在另一份文件里”，程序能不能接着读取？如果那份文件不存在，整个任务会不会直接报错退出？如果提供两个不同的工具，模型能不能选出当前需要的那个？

这一阶段，我围绕这三个问题完成了三次实验。最终的运行结果是：程序先列出可用文件，再连续读取两份资料，第四次模型请求给出正确的汇总，停止原因是 `stop`。

## 把“一次调用”接成循环

第一次实验使用下面的问题：

```powershell
python tool_call.py "请先读取 project.txt，再读取其中提到的任务文件，最后汇总项目名称、实验编号和下一步任务。"
```

运行中，每次执行工具前都要输入 `y`。这次我确认了两次，对应两次文件读取。

实际过程是：

```text
第 1 次模型请求
  → 模型提出 read_file("project.txt")
  → 我输入 y，Python 读取项目资料

第 2 次模型请求：带上第一次工具请求和读取结果
  → 模型提出 read_file("next_step.txt")
  → 我输入 y，Python 读取任务资料

第 3 次模型请求：带上前两次工具请求和结果
  → 模型汇总两份文件，正常结束
  → finish_reason = stop
```

这次我已经真实运行成功：程序先后读取两份文件，第三次请求给出了正确的最终回答。

> 【截图 2：第二次读取】截取终端中第二次模型回复的 `tool_calls`、`next_step.txt` 参数，以及确认后的工具结果。配文：第一次读取结果进入下一轮请求后，模型继续提出读取任务文件。

> 【截图 3：第三次请求与最终回答】截取 `[第 3 次模型回复]`、`停止原因：stop` 和完整最终回答。配文：两次工具执行完成后，第三次请求根据两份真实资料汇总。

实现这个过程，最关键的地方是 `run_agent()`。下面是按实际代码整理的简化流程，省略了参数检查、打印和异常处理：

```python
for step in range(1, MAX_MODEL_CALLS + 1):
    response = call_model(request, api_key)
    choice = response["choices"][0]

    if choice["finish_reason"] == "stop":
        # 展示最终回答，结束任务
        return

    # 检查停止原因、请求次数、工具名称和参数
    # 用户确认后执行工具，得到 result

    request = {
        **request,
        "messages": [
            *request["messages"],
            assistant_tool_request,
            tool_result,
        ],
    }
```

模型每一轮都要重新收到完整的消息历史，才能知道上一轮请求过什么、工具实际返回了什么。

其中，每次工具操作会向历史追加两条消息。实际代码是：

```python
messages = [
    *request["messages"],
    {
        "role": "assistant",
        "content": message.get("content"),
        "tool_calls": calls,
    },
    {
        "role": "tool",
        "tool_call_id": tool_call["id"],
        "content": json.dumps(result, ensure_ascii=False),
    },
]
```

第一条保留模型提出的工具请求，第二条记录本地执行的结果。`tool_call_id` 用来说明：这个结果对应的是哪一个工具请求。

后续请求仍然使用 `tool_choice: "auto"`。因此，模型可以继续请求工具，也可以根据已经得到的资料直接回答。

这就是我目前实现的 Agent 循环：模型提出操作，程序检查并执行，把真实结果交回模型，再由模型决定下一步。

## 故意让一次读取失败

成功读取只是第一种情况。实际使用时，文件可能被改名、删除，也可能没有访问权限。

以前直接调用 `read_text()`，遇到文件不存在会抛出异常。如果程序就此退出，模型只知道自己提出过读取，收不到执行失败的结果。

这一阶段，我把能够预期的文件操作错误转换成了工具结果。例如，读取不存在的任务文件时，返回的是这样的结构：

```json
{
  "ok": false,
  "tool": "read_file",
  "error": {
    "type": "FileNotFoundError",
    "message": "文件工具执行失败，请检查文件是否存在、访问权限及 UTF-8 编码。"
  },
  "path": "next_step.txt"
}
```

这里展示的是程序定义的结果结构；模型后续如何解释错误，要以当次真实响应为准。

`ok: false` 明确表示工具执行失败。失败结果没有 `content`，避免把错误提示混成文件正文。程序也没有直接把本地异常字符串发给模型，而是保留错误类型和统一说明。

为了验证这个分支，我临时改名了任务文件，并明确要求模型先读取它。下面的 PowerShell 命令会在实验结束后恢复文件名；如果备份名已存在，会先停止，避免覆盖：

```powershell
if (Test-Path -LiteralPath .\workspace\next_step.txt.bak) {
    throw "备份文件已存在，请先检查后再实验。"
}

Rename-Item -LiteralPath .\workspace\next_step.txt -NewName next_step.txt.bak
try {
    python tool_call.py "请先读取 next_step.txt；如果读取失败，再读取 project.txt。最后告诉我项目名称、实验编号和下一步任务，无法确认的内容请明确说明。"
}
finally {
    Rename-Item -LiteralPath .\workspace\next_step.txt.bak -NewName next_step.txt
}
```

我的真实运行结果是：`next_step.txt` 读取失败后，模型改读了 `project.txt`，正确回答了项目名和实验编号，同时说明无法确认任务文件的内容。

这次实验中的备用路径由用户问题明确给出，所以它验证的是：错误结果能进入下一轮，模型能按要求改用另一个工具操作。它还不能证明模型面对所有失败都能自行找到解决办法。

> 【截图 4：读取失败的结果】截取工具返回的 `ok: false`、`FileNotFoundError` 和 `path`，保留它进入下一轮消息历史的位置。配文：文件读取失败被包装成工具结果，循环继续运行。

> 【截图 5：改读项目资料后的回答】截取后续 `read_file` 的 `project.txt` 参数和最终回答，重点保留“能够确认的项目名与实验编号”和“无法确认的任务内容”。配文：模型根据成功读取的资料作答，并说明缺失的信息。

从这一步开始，我意识到：工具结果不只提供资料，也会改变后续操作的依据。成功和失败，都需要有模型能识别的返回格式。

## 再给它一个工具：先看看有哪些文件

连续调用同一个 `read_file` 工具之后，下一步是让模型在不同工具之间做选择。

我增加了 `list_files`。它接受空参数对象 `{}`，只列出允许读取且确实存在的文件名，不读取正文。

核心实现只有一行：

```python
def list_files() -> list[str]:
    return [name for name in ALLOWED_FILES if (WORKSPACE / name).is_file()]
```

这里的 `ALLOWED_FILES` 仍然只有两份公开练习文件：

```python
ALLOWED_FILES = ("project.txt", "next_step.txt")
```

所以，它只会返回这两份文件中实际存在的普通文件。即使在目录里额外放一个 `private.txt`，当前工具也不会把它列出来。这个限制由 Python 代码执行，工具说明中的文字只是向模型介绍使用方式。

两份文件都存在时，工具返回的结构是：

```json
{
  "ok": true,
  "tool": "list_files",
  "files": [
    "project.txt",
    "next_step.txt"
  ]
}
```

`list_files` 告诉模型有哪些文件可用；`read_file` 提供选中文件的正文。它们处理的是同一项任务的不同步骤。

在本文固定的代码版本中，直接运行即可验证这个流程：

```powershell
python tool_call.py
```

默认问题是：

```text
请先列出可用的练习文件，再读取项目资料和其中提到的任务文件，最后汇总项目名称、实验编号和下一步任务。
```

这次真实运行的顺序如下：

| 模型请求 | 模型返回 | 本地程序执行 |
|---|---|---|
| 第 1 次 | 请求 `list_files` | 我确认后列出两份文件名 |
| 第 2 次 | 请求 `read_file` | 我确认后读取 `project.txt` |
| 第 3 次 | 请求 `read_file` | 我确认后读取 `next_step.txt` |
| 第 4 次 | 正常回答，`stop` | 展示最终汇总，结束循环 |

总共是 **4 次模型请求、3 次工具执行、3 次人工确认**。最后一次模型请求用来整理答案，没有继续执行工具。

> 【截图 6：列文件结果】截取第一次 `list_files` 请求、空参数 `{}` 和确认后的 `files` 列表。配文：工具先返回可用文件名，文件正文仍然需要后续读取。

> 【截图 7：第四次请求完成任务】截取 `[第 4 次模型回复]`、`停止原因：stop` 和最终汇总。配文：列目录、读项目资料、读任务文件完成后，第四次请求给出最终回答。

实际代码按模型返回的工具名称分发执行：

```python
if name == "read_file":
    path = arguments["path"]
    result = {
        "ok": True,
        "tool": name,
        "path": path,
        "content": read_file(path),
    }
else:
    result = {"ok": True, "tool": name, "files": list_files()}
```

这段代码前面已经检查过工具名：只接受 `read_file` 和 `list_files`。读取时必须提供一个合法的 `path`；列文件时必须传入空对象。检查通过之后，才进入人工确认和执行阶段。

## 循环还需要停得下来

有了循环以后，模型可能反复请求同一个失败操作，也可能一直觉得还需要更多资料。因此，我给这一版程序保留了明确的停止条件：

- `finish_reason` 是 `stop`：展示最终回答，结束循环。
- 用户没有输入 `y`：本轮不执行工具，也不再请求模型。
- 工具名称或参数不合法：停止，提示原因。
- 输出因为 `length` 等原因异常结束：本轮不执行工具。
- 达到模型请求次数上限：停止，并提示任务未完成。

当前上限是 `MAX_MODEL_CALLS = 5`，每轮只接受一个工具请求。如果第 5 次回复仍然要求执行工具，程序会停止，不执行这一轮工具。因为即使执行了，也已经没有下一次模型请求来消费它的结果。

文件不存在、权限不足、UTF-8 解码失败等文件执行错误，会作为 `ok: false` 返回给模型。它们与非法工具请求的处理方式不同：前者是一次允许操作的执行结果，后者没有通过程序的检查。

另外，`stop` 只说明模型正常结束了回复。任务有没有完成，还要看实际工具结果和最终答案是否满足问题。前面的失败实验就可能正常结束，但任务文件的内容仍然无法确认。
