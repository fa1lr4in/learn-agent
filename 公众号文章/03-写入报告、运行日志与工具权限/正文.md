# 从零开发 Agent（三）：写文件、留日志，以及一次真实的工具调用故障

上一篇，我的 Python Agent 已经可以连续读取文件，在读取失败后拿到错误反馈，也能先列文件、再读取资料。

这一阶段，我给它安排了一个更完整的任务：读取项目资料和任务文件，整理成报告，真正保存到本地。同时，把每一步的请求、执行结果和结束原因记录下来。

过程中还遇到了一次真实的故障：我以为模型会一轮读取一个文件，它却在同一条回复里提出了两个读取请求，程序直接停止了。

这篇文章记录从写出第一份报告，到定位并修复这个问题的过程。最后的真实运行结果是：4 次模型请求完成任务，两份文件在同一轮读取，写入仍需人工确认，报告内容正确，日志以 `reason: stop` 结束。

## 把终端里的执行过程保存下来

随着工具变多，终端输出也越来越长。遇到问题时，我需要回头找：模型第几次请求了什么？我有没有确认？文件工具实际返回了什么？

所以，这一阶段增加了运行日志。

每次运行 `tool_call.py`，程序都会新建一个 `.jsonl` 文件，并在终端显示路径。例如，我这次成功任务的文件是：

```text
logs/run-20261017-183936-327109.jsonl
```

JSONL 的形式很直接：每一行是一个完整的 JSON 对象，一行记录一个事件。程序写入一条就刷新一次，方便在任务中途查看已经完成的步骤。

日志中有六类事件：

| 事件 | 含义 |
|---|---|
| `run_start` | 本次运行开始，记录请求上限和权限策略 |
| `model_request` | 准备发送的模型请求体 |
| `model_response` | 模型服务返回的 JSON |
| `tool_approval` | 某个工具是否获准执行，以及授权来源 |
| `tool_result` | 工具实际执行的结果 |
| `run_end` | 结束原因，异常时还记录异常类型 |

核心写入函数是：

```python
def record_event(log_file, event, **details):
    if log_file is None:
        return
    entry = {
        "time": datetime.now(timezone.utc).isoformat(),
        "event": event,
        **details,
    }
    log_file.write(json.dumps(entry, ensure_ascii=False) + "\n")
    log_file.flush()
```

请求和响应分别在模型调用前后记录；工具授权在执行前记录，工具结果在执行后记录。

日志保存的是请求体、回复和工具内容，API Key 与 HTTP 请求头不进入这些日志事件。问题和文件正文会保存在日志里，日志目录作为本地运行数据被 Git 忽略。

这些记录用于回看过程，程序下一次启动时不会自动把它们加载为模型的会话历史。

可以在 PowerShell 中提取最新一份日志的事件顺序：

```powershell
$runLog = Get-ChildItem -LiteralPath .\logs -Filter *.jsonl -File |
    Sort-Object LastWriteTime | Select-Object -Last 1

$events = Get-Content -LiteralPath $runLog.FullName -Encoding UTF8 |
    ForEach-Object { $_ | ConvertFrom-Json }

$events | Select-Object event, step, tool, reason | Format-Table -AutoSize
```

> 【截图 3：运行事件顺序】截取终端显示的日志路径和事件表，保留最后的 `run_end` 与 `stop`。配文：每次模型请求和工具执行都留下记录，关闭终端后仍可回看。

## 把“是否执行”变成本地策略

最初，每执行一个工具都要输入一次 `y`。默认任务包含列文件、两次读取和一次写入，总共需要确认四次。

随后，我增加了一个命令参数：

```powershell
python tool_call.py --auto-read
```

它表示我允许这次运行自动列出、读取两份公开练习资料，并把结果发送给 DeepSeek。写入报告时，程序仍然展示内容并等待确认。

| 工具 | 默认运行 | 加上 `--auto-read` |
|---|---|---|
| `list_files` | 每次确认 | 自动允许 |
| `read_file` | 每次确认 | 自动允许 |
| `write_file` | 每次确认 | 每次确认 |

这个选择由本地启动参数决定。模型提出工具请求后，程序先检查名称、参数和文件范围，再进入授权分支。

实际判断的关键部分是：

```python
if auto_read and name in ("read_file", "list_files"):
    approved, source = True, "auto_read"
else:
    answer = input(...)
    approved, source = answer.strip().lower() == "y", "user"
```

这里省略了提示文本，保留权限判断本身。`source` 会写进 `tool_approval` 日志：`auto_read` 表示读取策略批准，`user` 表示人工确认；`approved` 表示这次是否获准执行。

我在真实验证中选择了确认写入。拒绝写入后保留原文件、非法路径仍被拦截等分支，则由离线测试检查。

## 一次没有预料到的停止

第一次验证自动读取策略时，程序成功列出了文件，却在第 2 次模型回复后停止了。

终端中的报错是：

```text
本次实验停止：当前每轮只处理一个工具请求，请让模型分轮调用。
```

当时第 2 次回复的 `tool_calls` 列表里，实际包含两个读取请求。下面保留当次返回中的调用 ID、工具名和参数，省略其他字段：

```json
{
  "tool_calls": [
    {
      "id": "call_00_84BCtTxYyr7oBvZpnc4F3772",
      "function": {
        "name": "read_file",
        "arguments": "{\"path\": \"project.txt\"}"
      }
    },
    {
      "id": "call_01_EJimA97euXwMXRPJL2Fj2560",
      "function": {
        "name": "read_file",
        "arguments": "{\"path\": \"next_step.txt\"}"
      }
    }
  ]
}
```

> 【截图 4：失败现场】截取第 2 次模型回复中的两个 `read_file` 请求，以及下面的停止提示。配文：模型在一个回复里提出两次读取，触发了早期程序只接受一个调用的限制。

早期代码为简化学习，保留了下面的限制：

```python
if len(calls) != 1:
    raise ValueError("当前每轮只处理一个工具请求，请让模型分轮调用。")
```

系统指令虽然写着“每轮最多调用一次”，这次模型仍返回了两个调用。`tool_calls` 本身是一个列表，程序需要处理这个实际返回的列表。

日志也帮我缩小了范围：这次任务只发生了两次模型请求，授权记录只有第一次 `list_files` 的自动批准，最后是 `run_end`、`reason: error`。问题发生在程序检查第 2 次回复时，两次读取还没有执行。

## 一条回复里的多个调用，怎样交回结果

修复之后，程序分两步处理同一回复中的调用。

首先，检查整组调用的工具名称、参数和 ID。全部通过后，再按模型返回的顺序逐个确认、执行并记录结果。每个调用都有自己的 `tool_call_id`，同轮 ID 不能重复。

同一轮的执行顺序是：

```text
模型回复：请求读取 project.txt、next_step.txt
  ↓
检查两次调用的参数和 ID
  ↓
批准并执行第一次读取 → 记录第一个结果
  ↓
批准并执行第二次读取 → 记录第二个结果
  ↓
把两份结果一起带入下一次模型请求
```

历史消息的拼接也要对应起来：一条 `assistant` 消息保留完整的工具请求列表，后面分别追加两条 `tool` 消息。

```text
assistant：tool_calls 包含两个读取请求
tool：第一个读取结果，对应第一个调用 ID
tool：第二个读取结果，对应第二个调用 ID
```

程序按顺序执行这些调用。一个文件读取失败时，会记录 `ok: false`，继续处理同轮其他允许的调用。用户拒绝时，则立即停止被拒绝的工具和后续工具；此前已经执行的操作会保留。

这几种分支都补进了测试，原先只允许一个调用的判断也被替换掉了。

## 修复后的真实运行

重新运行同一个命令：

```powershell
python tool_call.py --auto-read
```

这次完整成功，实际过程如下：

| 模型请求 | 模型提出的操作 | 本地执行 |
|---|---|---|
| 第 1 次 | `list_files` | 自动批准，列出两份资料 |
| 第 2 次 | 两个 `read_file` | 分别自动批准，顺序读取两份资料 |
| 第 3 次 | `write_file` | 展示报告，等待人工确认后写入 |
| 第 4 次 | 最终回答 | 正常结束，日志记录 `reason: stop` |

总共执行了 4 个工具，但只请求了 4 次模型。其中两次读取共用了一条模型回复。

此前分轮读取时，完整任务需要 5 次模型请求。因此，模型请求次数和工具执行次数需要分别看，不能把“每轮”固定理解成“执行一个工具”。

从成功日志中提取授权记录：

```powershell
$events |
    Where-Object { $_.event -eq "tool_approval" } |
    Select-Object step, tool, approved, source |
    Format-Table -AutoSize
```

这次记录中的字段值是：

```text
step  tool        approved  source
1     list_files  True      auto_read
2     read_file   True      auto_read
2     read_file   True      auto_read
3     write_file  True      user
```

两个读取的 `step` 都是 `2`，各自的 `tool_call_id` 不同。`step` 表示第几次模型请求，调用 ID 用来对应某个具体工具的请求和结果。
