# 从零开发 Agent（五）：让代码修改可检查、可撤回

上一篇，我让自己开发的 Agent 修改一个多文件 Python 项目，为统计函数增加最小值和最大值，再运行测试验收。它已经走通了“读取代码、保存修改、执行程序、根据结果继续处理”的过程。

接下来，使用上的几个问题逐渐显现：项目文件多起来以后，怎样找到要改的位置？只改一行代码，是否还需要重新生成整个文件？测试通过以后，怎样核对这次到底改了什么？如果不想保留这次修改，又该恢复到哪里？

这一阶段，我补上了代码搜索、局部编辑、项目目录选择、命令执行，以及修改检查和撤回。同时，把逐渐变长的入口文件拆成几个职责明确的模块。

本文用一个完整任务记录这些变化：把入口文件的输入从 `[5, 10, 15]` 改成 `[6, 12, 18]`，运行测试和入口，查看差异，再撤回这次修改。

这次真实任务中，模型还走错过一次目录。工具把错误返回以后，它重新检查项目根目录，继续完成了任务。这个小插曲也很适合观察：Agent 怎样利用反馈调整下一步。

项目地址：[fa1lr4in/learn-agent](https://github.com/fa1lr4in/learn-agent)。

## 2. 准备一个修改前就有内容的项目

练习项目仍然很小：

```text
workspace/demo_project/
├── README.md
├── main.py
├── test_stats.py
└── src/
    └── stats.py
```

`main.py` 准备输入，调用 `src/stats.py` 中的 `summarize()`；`test_stats.py` 验证普通列表、空列表、单个数字和负数四种情况。

固定提交保留了课程最初的业务代码。为了接上上一篇已经完成的功能，需要在这个新副本里补回 `min`、`max`，并把入口输入设成 `[5, 10, 15]`。下面的准备命令只在刚克隆的副本中执行一次：

```powershell
@'
from pathlib import Path

project = Path('workspace/demo_project')
main = project / 'main.py'
stats = project / 'src/stats.py'
main_text = main.read_text(encoding='utf-8')
stats_text = stats.read_text(encoding='utf-8')
old_input = 'values = [12, 18, 30]'
marker = '        "average": total / count if count else 0.0,\n'
extra = (
    '        "min": min(values) if count else None,\n'
    '        "max": max(values) if count else None,\n'
)
assert main_text.count(old_input) == 1, '请先核对固定版本的 main.py'
assert stats_text.count(marker) == 1 and '"min"' not in stats_text, '请先核对固定版本的 stats.py'
main.write_text(main_text.replace(old_input, 'values = [5, 10, 15]'), encoding='utf-8')
stats.write_text(stats_text.replace(marker, marker + extra), encoding='utf-8')
print('已准备好本文练习项目。')
'@ | python -B -X utf8 -
if ($LASTEXITCODE -ne 0) { throw "练习项目准备失败，请检查输出。" }

$project = (Resolve-Path -LiteralPath .\workspace\demo_project).Path
$beforeHash = (Get-FileHash -LiteralPath (Join-Path $project "main.py") -Algorithm SHA256).Hash

python -B -X utf8 .\workspace\demo_project\test_stats.py
python -B -X utf8 .\workspace\demo_project\main.py
git status --short -- workspace/demo_project
```

预期四项业务测试通过，入口输出为：

```text
{'count': 3, 'total': 30, 'average': 10.0, 'min': 5, 'max': 15}
```

Git 状态会显示 `main.py` 和 `src/stats.py` 已有修改。这正好提供了一个有用的实验条件：**Agent 开始工作以前，项目里已经存在尚未提交的内容。后面的撤回需要保留这些内容。**

`$beforeHash` 保存了入口文件此时的 SHA-256，最后用它核对恢复后的内容是否与现在一致。

> 【截图 2：任务开始前】在编辑器中展示 `main.py` 的 `[5, 10, 15]` 和 `stats.py` 的五个返回字段；终端展示四项测试通过、入口输出，以及两个已有修改的文件。

## 3. 选择项目目录，让模型自己定位代码

此前，工具默认在 learn-agent 自带的 `workspace` 中工作。现在增加了 `--workspace`，可以把一个已有项目设为本次任务的根目录。

这里选择的是 `workspace/demo_project`。选定以后，工具看到的 `main.py` 就是这个项目的入口，`src/stats.py` 就是业务模块。工具路径统一相对选定根目录解析。

完整任务如下。先预览，再正式调用模型：

```powershell
$taskPrompt = @'
请先在项目根目录搜索 values = 并读取命中的入口文件，再用 edit_file 将 main.py 的输入从 [5, 10, 15] 改为 [6, 12, 18]。
随后用 run_command 执行 python -m unittest -v test_stats.py，再执行 python main.py。
保留其他文件和已有内容，最后简要说明修改与验证结果。
'@

python -B -X utf8 tool_call.py --workspace $project --auto-read --preview $taskPrompt
```

预览只展示请求，不联网、不执行工具，也不创建运行日志。核对开头的工作目录和工具说明后，继续执行：

```powershell
python -B -X utf8 tool_call.py --workspace $project --auto-read $taskPrompt
```

`--auto-read` 会自动批准目录浏览、搜索和读取。编辑和两次命令运行仍分别询问，检查内容后输入 `y`。

这次真实运行并没有一开始就找到正确路径。模型先向工具传入 `path: "demo_project"`，但当前根目录已经是 `demo_project`，实际查找的位置多了一层，于是搜索和列目录都失败了。

收到错误以后，模型改为列出 `.`，再从 `.` 搜索，找到了 `main.py`。

这个过程提醒我：工作目录虽然写在系统指令里，模型仍然可能使用错误路径。工具需要检查实际目录，并把真实结果交回循环，模型才能据此修正。

搜索工具的请求可以表示为：

```json
{
  "query": "values =",
  "path": ".",
  "max_results": 20
}
```

`search_text` 返回路径、从 1 开始的行号和命中行摘要。当前版本做区分大小写的字面搜索，结果数量受到限制；`truncated: true` 表示结果没有展示完整，需要缩小范围继续搜索。

搜索范围同样影响结论。比如只在 `src` 搜索 `summarize`，能找到函数定义，却不会找到根目录 `main.py` 中的导入和调用。看见一条匹配，只能说明本次搜索范围内的情况。

## 4. 只改一处，并在保存前展示差异

以前使用 `write_file` 时，需要给出完整的新文件。现在增加了 `edit_file`，用旧文本和新文本表达局部替换：

```json
{
  "path": "main.py",
  "old_text": "values = [5, 10, 15]",
  "new_text": "values = [6, 12, 18]"
}
```

宿主程序先读取当前文件，检查旧文本是否恰好匹配一处，再计算修改后的内容和差异。确认前会展示：

```diff
-    values = [5, 10, 15]
+    values = [6, 12, 18]
```

这里选择“恰好一处”，是为了让修改位置足够明确。旧文本不存在或出现多次时，工具返回 `EditConflict`，要求重新读取或补充上下文。

确认前的差异还需要与真正保存时的文件对应。`learn_agent/tools.py` 中的 `apply_edit()` 做了第二次检查：

```python
def apply_edit(path: str, original: bytes, updated: bytes) -> None:
    """Save only if the file still matches the snapshot shown for approval."""
    target = resolve_write_path(path)
    if target.read_bytes() != original:
        raise EditConflict("预览后文件已变化，未覆盖；请重新读取并准备编辑。")
    checkpoints.apply_change(target, updated, lambda: target.write_bytes(updated))
```

用户查看差异、准备确认的这段时间里，编辑器或其他程序也可能改动文件。如果磁盘内容已经变化，之前展示的差异就过期了，程序会拒绝覆盖。

本次输入 `y` 后，工具结果中的关键字段为：

```json
{
  "ok": true,
  "tool": "edit_file",
  "path": "main.py",
  "replacements": 1
}
```

这是实际返回结果的字段节选，完整结果还包含差异。此前的单独编辑实验也验证过：输入 `n` 时不保存修改，任务随即停止，已经完成的操作保留。

> 【截图 4：确认局部编辑】截取终端中的差异、确认提示，以及允许后的 `ok: true`、`replacements: 1`。编辑器中可以同时展示入口的新输入。

## 5. 用命令运行测试，再检查实际输出

原来的 `run_python` 适合直接运行一个 `.py` 文件。要支持 `python -m unittest` 这种带参数的调用，还需要更通用的 `run_command`。

模型提交的命令参数是一个字符串数组：

```json
{
  "command": ["python", "-m", "unittest", "-v", "test_stats.py"],
  "path": ".",
  "timeout": 30
}
```

第一个元素是程序，其余元素分别作为参数。`path` 决定命令在哪个项目子目录中执行，`timeout` 决定最长等待时间。这里的 `python` 会被替换成启动 Agent 的同一个 Python 解释器，减少环境不一致的问题。

底层以 `subprocess.Popen(shell=False)` 启动程序，因此数组中的参数不会自动被当成管道、重定向或一整段 shell 脚本解释。运行前，终端会展示实际程序、参数、工作目录和时限。

本次两次命令都经过人工确认，得到以下结果：

| 命令 | 退出码 | 输出与判定 |
| --- | --- | --- |
| `python -m unittest -v test_stats.py` | `0` | 四项业务测试全部通过 |
| `python main.py` | `0` | 输出数量 3、总和 36、平均值 12.0、最小值 6、最大值 18 |

测试成功报告位于 `stderr`，内容如下，耗时以实际运行结果为准：

```text
test_empty_list (test_stats.SummarizeTests.test_empty_list) ... ok
test_negative_numbers (test_stats.SummarizeTests.test_negative_numbers) ... ok
test_regular_numbers (test_stats.SummarizeTests.test_regular_numbers) ... ok
test_single_number (test_stats.SummarizeTests.test_single_number) ... ok

----------------------------------------------------------------------
Ran 4 tests in 0.000s

OK
```

入口的 `stdout` 则是：

```text
{'count': 3, 'total': 36, 'average': 12.0, 'min': 6, 'max': 18}
```

两次命令的 `timed_out`、`stdout_truncated`、`stderr_truncated` 均为 `false`。程序会分别记录超时和输出截断，模型需要结合这些标记、退出码与输出判断结果。

四项测试检查统计函数在固定输入下的行为，运行入口则核对这次改过的输入有没有真正生效。两者一起看，才能把“函数仍满足验收条件”和“入口已使用新数据”对应起来。

## 6. 从日志看清这次任务经过了什么

这次真实运行共请求模型 **7 次**，提出 **8 次工具调用**，其中前两次工具调用因路径错误失败，之后完成纠正。人工确认了 **3 次**：一次编辑、两次命令执行。

| 模型请求 | 提出的操作 | 实际结果 |
| --- | --- | --- |
| 第 1 次 | 在 `demo_project` 搜索并列目录 | 当前根目录已是该项目，两项均失败 |
| 第 2 次 | 列出 `.` 并搜索 `values =` | 成功定位入口 |
| 第 3 次 | 读取 `main.py` | 取得当前输入和源码 |
| 第 4 次 | 局部编辑 `main.py` | 确认后替换一处 |
| 第 5 次 | 执行测试命令 | 确认后，四项测试通过 |
| 第 6 次 | 执行入口命令 | 确认后，输出总和 36 等统计值 |
| 第 7 次 | 给出最终回答 | 正常结束，停止原因 `stop` |

这个表来自本次日志。重新调用模型时，工具的分组和请求次数可能变化，不需要强求与表格完全一致。

任务完成后，在同一窗口选出刚生成的日志，核对工具结果、授权来源和结束原因：

```powershell
$runLog = Get-ChildItem -LiteralPath .\logs -Filter *.jsonl -File |
    Sort-Object LastWriteTime | Select-Object -Last 1
if (-not $runLog) { throw "尚未找到正式运行的日志。" }

$events = Get-Content -LiteralPath $runLog.FullName -Encoding UTF8 |
    ForEach-Object { $_ | ConvertFrom-Json }

$events | Where-Object { $_.event -eq "tool_result" } |
    ForEach-Object {
        [pscustomobject]@{
            step      = $_.step
            tool      = $_.result.tool
            path      = $_.result.path
            ok        = $_.result.ok
            exit_code = $_.result.exit_code
        }
    } | Format-Table -AutoSize

$events | Where-Object { $_.event -eq "tool_approval" } |
    Select-Object step, tool, approved, source |
    Format-Table -AutoSize

$events | Select-Object -Last 1 | ConvertTo-Json
```

本次编辑和运行的授权来源为 `user`，浏览、搜索和读取为 `auto_read`。最后一条是 `run_end`，`reason` 为 `stop`。之后查看差异和撤回，继续使用这里保存的 `$runLog`，不用重新选择。

## 7. 查看差异，再决定是否撤回

任务完成以后，可以直接检查本次文件工具记录的修改：

```powershell
python -B -X utf8 tool_call.py --workspace $project --diff $runLog.FullName
```

这里应看到 `main.py` 从 `[5, 10, 15]` 变为 `[6, 12, 18]` 的差异。

终端还会展示 Git 状态，里面仍然可能有 `main.py` 和 `src/stats.py` 两个修改。原因在前面的准备阶段已经出现：它们在本次 Agent 任务之前就与 Git 中的版本不同。

**本次差异只包含这次经过文件工具保存的修改。**因此，`stats.py` 里的 `min`、`max` 不会被算作这次任务新增的内容，也不应该在撤回时丢掉。

接着尝试撤回：

```powershell
python -B -X utf8 tool_call.py --workspace $project --undo $runLog.FullName
```

程序先展示反向差异，再询问确认。第一次可以输入 `n`，观察取消提示。随后检查入口文件仍然保留新输入：

```powershell
Get-Content -LiteralPath (Join-Path $project "main.py") -Encoding UTF8
```

再次执行同一条撤回命令，这次检查差异后输入 `y`：

```powershell
python -B -X utf8 tool_call.py --workspace $project --undo $runLog.FullName
```

允许后，预期返回：

```json
{
  "ok": true,
  "restored": [
    "main.py"
  ],
  "removed": []
}
```

最后独立核对恢复结果：

```powershell
(Get-FileHash -LiteralPath (Join-Path $project "main.py") -Algorithm SHA256).Hash -eq $beforeHash
python -B -X utf8 .\workspace\demo_project\main.py
python -B -X utf8 .\workspace\demo_project\test_stats.py
python -B -X utf8 tool_call.py --workspace $project --diff $runLog.FullName
git status --short -- workspace/demo_project
```

预期哈希比较为 `True`，入口重新输出总和 30、平均值 10.0、最小值 5、最大值 15，四项测试仍然通过。检查点显示尚待撤回 0 个文件、已撤回 1 个文件。

Git 中准备阶段留下的两个修改仍然存在。这表明恢复目标是本次任务修改前的文件内容，原先已经完成的功能得到保留。

原始开发目录中这次任务的检查点已经标记为 `undone`，入口文件也与保存的修改前字节完全一致。上面的新副本用于重新演示完整过程；取消确认和冲突等分支另外由离线测试覆盖。

## 8. 撤回能力具体放在了哪里

做到这里，我也专门厘清了一个概念：撤回由本地程序实现，属于这个编程产品增加的能力。模型、工具和执行循环已经可以组成一个最小 Agent；文件检查点是在此基础上加入的工程功能。

每次新任务会在 JSONL 日志旁保存一个同名检查点，例如：

```text
logs/
├── run-日期-时间.jsonl
└── run-日期-时间.checkpoint.json
```

`learn_agent/checkpoints.py` 保存本次通过 `write_file`、`edit_file` 修改过的文件。一个文件第一次被修改时保存 `before`，之后更新 `after` 和文件状态。下面是 `Checkpoint.change()` 中记录内容的节选：

```python
entry = {"before": previous["before"] if previous else encode(before),
         "after": encode(updated), "fingerprint": None, "state": "pending"}
self.data["files"][key] = entry
```

原始内容按字节保存并编码进 JSON。同一个文件在本次任务中改过多次，仍然保留第一次修改前的 `before`。完整实现还会先保存记录，再执行修改，随后核对实际写入结果。

撤回时需要检查当前文件是否仍与记录中的修改后版本一致。若文件后来被手动改动、重新保存、删除或重定向，程序会拒绝自动恢复，避免覆盖后续工作。用户确认以后，真正写回前还会再检查一次。

这个实现有明确范围：

- 只追踪本次 `write_file`、`edit_file` 的修改；命令、其他程序或手动操作产生的变更不自动纳入。
- 原有文件恢复修改前内容；本次新建、且仍保持本次版本的文件，撤回时删除。
- 不执行 Git 的重置、检出或清理，也不修改暂存区和提交记录。
- 不自动合并后续改动；多文件恢复途中发生异常，可能留下部分已恢复的状态，需要重新核对记录。
- 查看和撤回都不调用模型，不执行日志里过去的工具请求。

检查点属于本地备份，位于已被 Git 忽略的 `logs` 目录中。它与运行日志一样，可能包含项目源码，公开项目时不需要把这些运行资料一并提交。

这一阶段，代码也按职责拆开了：

| 文件 | 主要职责 |
| --- | --- |
| `tool_call.py` | 命令行参数、项目选择、请求预览、检查和撤回入口 |
| `learn_agent/model.py` | 模型配置、密钥读取和 API 请求 |
| `learn_agent/loop.py` | 请求模型、处理工具调用、携带结果继续，以及停止条件 |
| `learn_agent/tools.py` | 工具注册、参数检查、搜索、读写与局部编辑 |
| `learn_agent/permissions.py` | 工作目录、路径边界和操作确认 |
| `learn_agent/commands.py` | 带参数命令的执行、输出限制和进程清理 |
| `learn_agent/checkpoints.py` | 本次文件修改记录、差异检查和受控撤回 |
| `learn_agent/events.py` | 运行事件与历史恢复 |

工具说明和工具实现统一放进注册表。比如，发送给模型的说明直接从同一份注册表生成：

```python
def tool_schemas() -> list[dict]:
    return [tool.schema for tool in TOOL_REGISTRY.values()]
```

循环再根据工具名称查找对应实现。新增 `run_command` 时，不需要在 Agent 循环里增加一套专门分支。这样拆分以后，排查模型请求、工具行为或文件恢复的问题，都更容易找到对应位置。

## 9. 这一步让项目发生了什么变化

前一阶段，重点是让 Agent 完成一次项目修改。这一阶段，开始把完成任务所需的过程交给使用者核对：先看定位结果，再看编辑差异，分别批准运行，最后检查实际修改和恢复结果。

这次任务只改了一行输入，却覆盖了几个容易混淆的问题：工具路径相对哪个目录、搜索结果有没有覆盖全项目、确认的差异是否仍然有效、测试报告为什么出现在 `stderr`，以及 Git 中已有的修改该怎样保留。

目前的工具仍然有边界。四项业务测试只覆盖已经定义的输入；命令执行依然使用当前账户的权限，项目路径检查并不构成操作系统沙箱；文件撤回只处理检查点明确记录的内容。

不过，现在可以用一组具体证据说明一次任务做了什么：搜索和读取结果、实际保存的代码差异、命令退出码、测试报告、入口输出，以及撤回后的文件哈希。

后续开发会进入会话和长任务管理，把消息、工具执行和任务状态保存得更清楚。本文先停在这个可以完整复现的节点：一次修改能被找到、被确认、被验证，也能在支持的条件下恢复。
