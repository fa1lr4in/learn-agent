# 从零开发 Agent（五）：让代码修改可检查、可撤回

上一篇，我让自己开发的 Agent 修改一个多文件 Python 项目，为统计函数增加最小值和最大值，再运行测试验收。它已经走通了读取代码、修改文件、运行程序和根据结果继续处理的过程。

接下来，几个使用上的问题逐渐显现：项目文件多了，怎样定位要改的代码？只改一行，是否还需要重新生成整个文件？测试通过以后，怎样确认这次到底改了什么？不想保留修改时，又应该恢复到哪个版本？

这一阶段，我补上了代码搜索、局部编辑、项目目录选择、命令执行，以及修改检查和撤回。同时，把逐渐变长的入口文件拆成了几个职责明确的模块。

本文用一个小实验记录这些变化：把入口输入从 `[5, 10, 15]` 改为 `[6, 12, 18]`，验证结果，再恢复原内容。

为了逐段观察过程，实验分成搜索、编辑和测试三个任务。每段结束后固定保存对应的日志路径，后面的差异检查和撤回始终使用编辑任务的日志。这样既能逐步复现，也能把每张截图和实际执行的操作对应起来。

项目地址：[fa1lr4in/learn-agent](https://github.com/fa1lr4in/learn-agent)。

## 2. 准备一个已经有修改的项目

练习项目仍然很小：

```text
workspace/demo_project/
├── README.md
├── main.py
├── test_stats.py
└── src/
    └── stats.py
```

`main.py` 准备输入，调用 `src/stats.py` 中的 `summarize()`；`test_stats.py` 检查普通列表、空列表、单个数字和负数四种情况。

固定提交保留了最初的业务代码。先在刚克隆的副本里补回上一篇完成的 `min`、`max`，并把入口输入设为 `[5, 10, 15]`。这组初始化命令只执行一次；需要从头重做时，重新执行第 1 节创建新的副本。

**截图 2 的复现命令：**

```powershell
@'
from pathlib import Path

project = Path('workspace/demo_project')
main = project / 'main.py'
stats = project / 'src/stats.py'
main_text = main.read_text(encoding='utf-8')
stats_text = stats.read_text(encoding='utf-8')
old_input = 'values = [12, 18, 30]'
marker = '        "average": total / count if count else 0.0,\n'
extra = (
    '        "min": min(values) if count else None,\n'
    '        "max": max(values) if count else None,\n'
)
assert main_text.count(old_input) == 1, '请先核对固定版本的 main.py'
assert stats_text.count(marker) == 1 and '"min"' not in stats_text, '请先核对固定版本的 stats.py'
main.write_text(main_text.replace(old_input, 'values = [5, 10, 15]'), encoding='utf-8')
stats.write_text(stats_text.replace(marker, marker + extra), encoding='utf-8')
print('已准备好本文练习项目。')
'@ | python -B -X utf8 -
if ($LASTEXITCODE -ne 0) { throw "练习项目准备失败，请检查输出。" }

$project = (Resolve-Path -LiteralPath .\workspace\demo_project).Path
$logsDir = Join-Path $reproDir 'logs'
$beforeHash = (Get-FileHash -LiteralPath (Join-Path $project 'main.py') -Algorithm SHA256).Hash

Get-Content -LiteralPath (Join-Path $project 'main.py') -Encoding UTF8
Get-Content -LiteralPath (Join-Path $project 'src\stats.py') -Encoding UTF8
python -B -X utf8 .\workspace\demo_project\test_stats.py
if ($LASTEXITCODE -ne 0) { throw "初始业务测试未通过。" }
python -B -X utf8 .\workspace\demo_project\main.py
git status --short -- workspace/demo_project
```

预期四项业务测试通过，入口输出：

```text
{'count': 3, 'total': 30, 'average': 10.0, 'min': 5, 'max': 15}
```

Git 状态会显示 `main.py` 和 `src/stats.py` 已有修改。这个初始条件很有用：**Agent 开始任务以前，项目里已经存在尚未提交的内容。最后撤回时，需要把这些原有内容保留下来。**

`$beforeHash` 保存了入口文件此时的 SHA-256，最后用它检查恢复后的文件是否与现在完全一致。

> 【截图 2：任务开始前】执行上面的命令，截取源码中的 `[5, 10, 15]`、`min` 与 `max`，以及四项测试通过、入口总和为 30 和两个文件的 Git 修改状态。内容较多时可以分两张截。

## 3. 在选定项目里搜索代码

此前，工具默认在 learn-agent 自带的 `workspace` 里工作。现在增加了 `--workspace`，可以把一个已有项目设为本次任务的根目录。

本文选择 `workspace/demo_project`。选定以后，工具路径中的 `main.py` 就是这个项目的入口，`src/stats.py` 就是业务模块；`.` 表示当前项目根目录。

这一节先单独验证搜索和读取，文件保持第 2 节的状态。

**截图 3 的复现命令：**

```powershell
$searchTask = @'
请使用 search_text 在项目根目录 . 中搜索 values =，再使用 read_file 读取命中的入口文件。
简要说明入口文件的相对路径、命中行号和当前输入。
本次只搜索和读取，不创建、修改或运行任何文件。
'@

python -B -X utf8 tool_call.py --workspace $project --auto-read --preview $searchTask
python -B -X utf8 tool_call.py --workspace $project --auto-read $searchTask
if ($LASTEXITCODE -ne 0) { throw "搜索任务异常结束，请先检查输出。" }

$searchLog = Get-ChildItem -LiteralPath $logsDir -Filter *.jsonl -File |
    Sort-Object LastWriteTime | Select-Object -Last 1
Write-Host "搜索任务日志：$($searchLog.FullName)"
```

第一条 Python 命令预览请求，不联网、不执行工具。第二条正式调用模型；`--auto-read` 自动允许目录浏览、搜索和读取。

预期搜索命中 `main.py` 中准备输入的那一行，读取后确认当前输入仍是 `[5, 10, 15]`。在本文固定源码中，这一行位于第 5 行。

搜索工具的参数可以表示为：

```json
{
  "query": "values =",
  "path": ".",
  "max_results": 20
}
```

`search_text` 返回相对路径、从 1 开始的行号和命中行摘要。当前版本做区分大小写的字面搜索，结果数量受到限制；`truncated: true` 表示还有未展示的匹配，需要缩小范围继续搜索。

范围也影响结论。只在 `src` 中搜索 `summarize`，会找到函数定义，却不会覆盖根目录入口里的导入和调用。因此，工具返回一处匹配，并不代表整个项目只有一处。

此前一次完整任务中，模型还曾把路径写成 `demo_project`。当根目录已经是这个项目时，这相当于多找了一层。工具返回失败后，它改为浏览和搜索 `.`，才找到入口。复现时模型可能直接使用正确路径，按实际结果记录即可。

## 4. 只改一处，保存前先看差异

以前使用 `write_file` 时，需要给出完整的新文件。现在增加了 `edit_file`，用旧文本和新文本表达局部替换：

```json
{
  "path": "main.py",
  "old_text": "values = [5, 10, 15]",
  "new_text": "values = [6, 12, 18]"
}
```

宿主程序先读取文件，检查旧文本是否恰好匹配一处，再计算修改后的内容和差异。旧文本不存在或出现多次时，返回 `EditConflict`，要求重新读取或补充上下文。

下面单独运行编辑任务。此时 `main.py` 应仍使用 `[5, 10, 15]`。命令运行到编辑确认时，先截差异，再输入 `y` 允许保存；保存后继续截取成功结果。

**截图 4 的复现命令：**

```powershell
$editTask = @'
请先读取 main.py，再只使用 edit_file 将 values = [5, 10, 15] 精确替换为 values = [6, 12, 18]。
只修改这一处，保留其他内容；不要运行代码或命令。
保存成功后简要说明工具结果。
'@

python -B -X utf8 tool_call.py --workspace $project --auto-read $editTask
if ($LASTEXITCODE -ne 0) { throw "编辑任务异常结束，请先检查输出。" }

$editLog = Get-ChildItem -LiteralPath $logsDir -Filter *.jsonl -File |
    Sort-Object LastWriteTime | Select-Object -Last 1
$afterEditHash = (Get-FileHash -LiteralPath (Join-Path $project 'main.py') -Algorithm SHA256).Hash
Write-Host "编辑任务日志：$($editLog.FullName)"
Get-Content -LiteralPath (Join-Path $project 'main.py') -Encoding UTF8
```

确认前应看到：

```diff
-    values = [5, 10, 15]
+    values = [6, 12, 18]
```

允许后，工具结果包含以下字段，完整结果还会返回差异：

```json
{
  "ok": true,
  "tool": "edit_file",
  "path": "main.py",
  "replacements": 1
}
```

如果这次输入 `n`，文件不会保存，任务会停止。需要继续本文实验时，重新执行本节编辑任务并允许保存；随后重新执行本节保存 `$editLog` 和 `$afterEditHash` 的命令，让它们对应成功的那次任务。

> 【截图 4：局部编辑】执行本节编辑命令，在确认前截取差异与提示；输入 `y` 后截取 `ok: true`、`replacements: 1`。最后一条 `Get-Content` 用来展示新输入 `[6, 12, 18]`。这几个画面均来自本节这组命令，可以分两张截。

差异展示后还需要防止文件被其他程序修改。`learn_agent/tools.py` 中的关键实现如下：

```python
def apply_edit(path: str, original: bytes, updated: bytes) -> None:
    """Save only if the file still matches the snapshot shown for approval."""
    target = resolve_write_path(path)
    if target.read_bytes() != original:
        raise EditConflict("预览后文件已变化，未覆盖；请重新读取并准备编辑。")
    checkpoints.apply_change(target, updated, lambda: target.write_bytes(updated))
```

用户查看差异、准备确认期间，编辑器也可能保存新内容。真正写回之前再比较一次文件，才能确认当前操作仍对应刚才展示的差异。

## 5. 执行测试命令，再检查入口输出

原来的 `run_python` 适合运行一个 `.py` 文件。要支持 `python -m unittest` 这类带参数的调用，还需要 `run_command`。

它接收一个字符串数组，第一个元素是程序，其余元素分别作为参数：

```json
{
  "command": ["python", "-m", "unittest", "-v", "test_stats.py"],
  "path": ".",
  "timeout": 30
}
```

这里的 `python` 会被替换为启动 Agent 的同一个 Python 解释器。`path` 指定项目内的工作目录，`timeout` 指定最长等待时间。底层以 `subprocess.Popen(shell=False)` 启动程序，不自动把参数解释成管道、重定向或一整段 shell 脚本。

这一节从第 4 节修改成功后的状态开始，只运行测试和入口。两次命令都需要检查提示并输入 `y`。

**截图 5 的复现命令：**

```powershell
$commandTask = @'
请依次使用 run_command，在项目根目录 . 执行以下两个命令：
1. python -m unittest -v test_stats.py
2. python main.py
两次 timeout 都设为 30。只运行和核对结果，不创建或修改文件。
最后根据 exit_code、stdout、stderr、超时与截断标记简要说明结果。
'@

python -B -X utf8 tool_call.py --workspace $project --auto-read $commandTask
if ($LASTEXITCODE -ne 0) { throw "命令任务异常结束，请先检查输出。" }

$commandLog = Get-ChildItem -LiteralPath $logsDir -Filter *.jsonl -File |
    Sort-Object LastWriteTime | Select-Object -Last 1
Write-Host "命令任务日志：$($commandLog.FullName)"
```

预期结果为：

| 命令 | 退出码 | 结果 |
| --- | --- | --- |
| `python -m unittest -v test_stats.py` | `0` | 四项业务测试通过 |
| `python main.py` | `0` | 总和 36、平均值 12.0、最小值 6、最大值 18 |

测试成功报告写在 `stderr`，大致如下，耗时以实际结果为准：

```text
test_empty_list (test_stats.SummarizeTests.test_empty_list) ... ok
test_negative_numbers (test_stats.SummarizeTests.test_negative_numbers) ... ok
test_regular_numbers (test_stats.SummarizeTests.test_regular_numbers) ... ok
test_single_number (test_stats.SummarizeTests.test_single_number) ... ok

----------------------------------------------------------------------
Ran 4 tests in 0.000s

OK
```

入口的 `stdout` 应为：

```text
{'count': 3, 'total': 36, 'average': 12.0, 'min': 6, 'max': 18}
```

两次命令的 `timed_out`、`stdout_truncated`、`stderr_truncated` 应为 `false`。这些字段分别反映超时和输出是否完整；模型需要结合退出码和实际输出判断，不能只看有没有错误文本。

四项测试检查函数在固定输入下的行为；入口输出则说明这次改过的数据已经生效。两者共同构成本次修改的验收依据。

> 【截图 5：测试与入口】执行本节命令任务，两次运行都输入 `y`。截取两次 `run_command` 的退出码、测试报告、入口输出及超时和截断标记；篇幅较长时分两张截。

## 6. 用三份日志对应三个任务

现在已经得到三份日志：`$searchLog` 对应搜索，`$editLog` 对应文件修改，`$commandLog` 对应测试和运行。

三次任务都会保存检查点，但只有编辑任务的检查点包含这次 `main.py` 的变化。后面需要撤回时，明确使用 `$editLog`。

**截图 6 的复现命令：**

```powershell
$taskLogs = @(
    [pscustomobject]@{ task = '搜索'; file = $searchLog }
    [pscustomobject]@{ task = '编辑'; file = $editLog }
    [pscustomobject]@{ task = '命令'; file = $commandLog }
)

foreach ($item in $taskLogs) {
    Write-Host "`n[$($item.task)任务] $($item.file.FullName)"
    $events = Get-Content -LiteralPath $item.file.FullName -Encoding UTF8 |
        ForEach-Object { $_ | ConvertFrom-Json }

    $events | Where-Object { $_.event -eq 'tool_result' } |
        ForEach-Object {
            [pscustomobject]@{
                step      = $_.step
                tool      = $_.result.tool
                path      = $_.result.path
                ok        = $_.result.ok
                exit_code = $_.result.exit_code
            }
        } | Format-Table -AutoSize

    $events | Where-Object { $_.event -eq 'tool_approval' } |
        Select-Object step, tool, approved, source |
        Format-Table -AutoSize

    $events | Select-Object -Last 1 | ConvertTo-Json
}
```

预期三个任务均以 `run_end.reason: stop` 正常结束。浏览、搜索和读取的授权来源为 `auto_read`；编辑和两次命令运行的授权来源为 `user`。

模型可能把多个工具放在同一条回复里，也可能分成多轮。复现时以实际工具记录为准，无需追求固定请求次数。检查的重点是：操作是否真实执行、由谁授权，以及工具结果怎样影响最终结论。

> 【截图 6：日志证据】运行上面的日志检查命令，截取带任务名称的工具结果、授权来源和结束记录。可以分别截编辑任务与命令任务，但要保留任务名称，避免把两份日志混为一次运行。

## 7. 先查看差异，再拒绝一次撤回

测试通过以后，还要检查这次保存了什么。这里继续使用第 4 节保存的 `$editLog`，项目当前仍应使用 `[6, 12, 18]`。

**截图 7 的复现命令，先查看差异并发起撤回：**

```powershell
python -B -X utf8 tool_call.py --workspace $project --diff $editLog.FullName
python -B -X utf8 tool_call.py --workspace $project --undo $editLog.FullName
```

第一条展示从 `[5, 10, 15]` 到 `[6, 12, 18]` 的正向差异。第二条展示反向差异，等待确认时输入 **`n`**，这次先不恢复。

取消以后，继续运行同一张截图的核对命令：

```powershell
Get-Content -LiteralPath (Join-Path $project 'main.py') -Encoding UTF8
(Get-FileHash -LiteralPath (Join-Path $project 'main.py') -Algorithm SHA256).Hash -eq $afterEditHash
```

预期仍能看到 `[6, 12, 18]`，哈希比较为 `True`，表示拒绝撤回没有改变文件。

检查输出里还会展示 Git 状态，里面可能同时列出 `main.py` 和 `src/stats.py`。它们在第 2 节就已经与 Git 中的初始版本不同。当前检查点只包含本次编辑工具造成的入口变化，不会把原有的 `min`、`max` 一并当作本次新增内容。

> 【截图 7：差异与拒绝】先运行本节前两条命令，在撤回提示处输入 `n`，截取反向差异与取消提示；再运行后两条核对命令，截取仍保留的新输入和 `True`。两组命令共同复现这一位置的画面。

## 8. 允许撤回，确认原有工作仍然保留

现在再次发起同一个编辑任务的撤回。这一次检查反向差异后输入 **`y`**。

**截图 8 的复现命令，先确认恢复：**

```powershell
python -B -X utf8 tool_call.py --workspace $project --undo $editLog.FullName
```

成功后应返回：

```json
{
  "ok": true,
  "restored": [
    "main.py"
  ],
  "removed": []
}
```

## 9. 文件检查点如何实现，代码又怎样组织

撤回由本地程序实现，属于这个编程产品增加的能力。模型、工具和执行循环已经可以组成一个最小 Agent；文件检查点是在此基础上加入的工程功能。

每次任务会在 JSONL 日志旁保存一个同名检查点：

```text
logs/
├── run-日期-时间.jsonl
└── run-日期-时间.checkpoint.json
```

`learn_agent/checkpoints.py` 只记录本次经过 `write_file`、`edit_file` 修改的文件。第一次修改前保存 `before`，之后更新 `after` 和文件状态。下面是 `Checkpoint.change()` 中的记录节选：

```python
entry = {"before": previous["before"] if previous else encode(before),
         "after": encode(updated), "fingerprint": None, "state": "pending"}
self.data["files"][key] = entry
```

原内容按字节保存并编码进 JSON。同一个文件在一次任务中改过多次，仍保留第一次修改前的 `before`。完整实现会先保存记录，再执行文件修改，并核对写入结果。

撤回前需要确认当前文件仍对应记录中的修改后版本。若它被其他程序改过、重新保存、删除或重定向，程序会拒绝自动恢复；确认之后，真正写回之前还会重新检查。

因此，这项能力有明确范围：

- 只追踪文件工具的修改，命令、其他程序和用户手动操作的变更不自动纳入。
- 原有文件恢复内容；本次新建且仍保持本次版本的文件，撤回时删除。
- 不执行 Git 重置、检出或清理，也不修改暂存区和提交记录。
- 不自动合并后续修改；多文件恢复途中发生异常时，可能需要核对部分完成的状态。
- 查看与撤回不调用模型，也不执行过去的工具请求。

检查点是本地备份，与运行日志一起放在被 Git 忽略的 `logs` 中。里面可能包含项目源码，公开仓库时不需要提交这些运行资料。

这一阶段还完成了工具注册与模块拆分：

| 文件 | 主要职责 |
| --- | --- |
| `tool_call.py` | 命令行参数、项目选择、预览、检查和撤回入口 |
| `learn_agent/model.py` | 模型配置、密钥读取与 API 请求 |
| `learn_agent/loop.py` | 模型与工具循环，以及停止条件 |
| `learn_agent/tools.py` | 工具注册、参数验证、搜索、读写和局部编辑 |
| `learn_agent/permissions.py` | 工作目录、路径边界和操作确认 |
| `learn_agent/commands.py` | 命令执行、输出限制与进程清理 |
| `learn_agent/checkpoints.py` | 文件修改记录、差异和受控撤回 |
| `learn_agent/events.py` | 运行事件与历史恢复 |

发送给模型的工具说明从同一份注册表生成：

```python
def tool_schemas() -> list[dict]:
    return [tool.schema for tool in TOOL_REGISTRY.values()]
```

循环再根据名称查找对应实现。新增 `run_command` 时，就不必在循环里增加一套专门的工具分支。排查模型请求、文件修改和进程运行问题，也更容易找到对应模块。

前一阶段的重点是完成一次项目修改；这一阶段，则把定位、确认、验证和恢复的过程交给使用者核对。

这个 Agent 仍然很小。四项业务测试只覆盖已有用例；命令使用当前账户权限，项目路径检查并不构成操作系统沙箱；撤回也只处理检查点明确记录的内容。

不过，一次任务现在已经有了一组具体证据：搜索结果、编辑差异、授权记录、真实测试与输出，以及恢复后的文件哈希。后续将继续学习会话和长任务管理，本文先停在这个可以完整复现的节点。
